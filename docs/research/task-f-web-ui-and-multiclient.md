# 调研:真实监控页面怎么做 + 我们能加什么数据图 + 多客户端能力

> 日期:2026-09-20 · 触发:用户问"页面还能怎么设计?多做点数据图;真实监控页面怎么实现的?
> 我们支持多个客户端吗?"(**这份是调研与方案, 不含实现**)
> 结论速览见 §1;要做的决定见 §8。

---

## 1. 结论速览(5 条)

1. **真实监控 Web 界面分三档**:①**厂商内置页**(海康/大华/Axis, 功能全但老气);
   ②**开源 NVR**(Frigate / Shinobi / ZoneMinder / Agent DVR, 现代但栈重);
   ③**播放器直连**(VLC/mpv/go2rtc 页面, 零 UI)。**我们的定位正好在 ①③ 之间**:
   设备自带页面 + 零安装 —— 这条路线是**对的**, 不需要换。
2. **实时传输的主流做法已经从 MJPEG 转向 MSE / WebRTC**。Frigate 官方文档写得最清楚:
   `jsmpeg`(MJPEG 家族, **默认无 go2rtc 时**使用, 帧率上限 10、720p、无音频、
   **更吃浏览器 GPU**)→ `mse`(go2rtc, 原生帧率/分辨率) → `webrtc`(原生 + 音频 + 双向对讲,
   要额外配置 8555 端口与 candidate)。**我们现在的 MJPEG 属于"最低门槛那一档"** ——
   优点是零依赖、任何浏览器都认; 代价是带宽高、无音频。
3. **值得偷的一个设计:按需/智能降级**。Frigate 默认 **"Smart Streaming"**：
   没有活动时**每分钟只更新一张图**, 一检测到运动就无缝切回实时流 —— 用"静态画面 = 无运动画面"
   这个洞察省带宽。**我们的"没人看就拆通道"是同一思路的粗粒度版**; 细粒度版见 §6-B。
4. **数据可视化的"标准配置"**(对照 Frigate 的 System 页与社区 Grafana 面板):
   码率 / 帧率 / **丢帧归因** / 队列水位 / 存储占用与健康 / 每摄像头状态。
   **这些数据我们已经有一大半**(见 §5), 只是**没有对外暴露、页面也没画**——
   所以"加数据图"这件事的**边际成本很低、观感提升很大**。
5. **多客户端**:RTSP **8 个**(验收里实测过 3 个同时)、MJPEG **4 个**(一帧只编一次**广播**给所有
   观看者 —— 这是我们的优势)、**回放 HTTP 是串行的(1 个)** —— 这一个才是真正的短板,
   也是 ADR-5 里写明的升级路径。详见 §4。

## 3. 真实监控页面怎么做的(按"层次"拆)

### 3.1 传输层(决定"能不能看、清不清楚、卡不卡")

| 方案 | 谁在用 | 优点 | 代价 |
|---|---|---|---|
| **MJPEG over HTTP** | 老式 IPC、厂商的单帧/多帧 HTTP 接口、Frigate 的 `jsmpeg` 模式 | **零依赖**:`<img>` 就行; 任何浏览器/任何年代都认 | 带宽高(每帧都是关键帧); 无音频; 帧率通常被限(10~15) |
| **MSE(fMP4 over WebSocket)** | Frigate 默认(配 go2rtc 时) | 原生帧率/分辨率, 延迟低, 不需要特殊端口 | 要服务端会 **fMP4/分片**; 浏览器兼容性有坑(iOS 17.1+、Firefox 仅 H.264) |
| **WebRTC** | Frigate(AI 对讲)、家用摄像头 App | 最低延迟、可双向音频 | 要信令 + DTLS/SRTP + candidate/STUN; 复杂度最高 |
| **HLS** | 大厂云平台、跨网观看 | 天然穿 CDN、兼容性最好 | 延迟大(切片); 要 TS/fMP4 复用器 |

**Frigate 文档里两条与我们直接相关的经验**:
- 摄像头编码选 **H.264**(避免 H.265/"smart codec"): 那些"增强码流"会**删关键帧**,
  导致开始播放更慢;
- **I 帧间隔 ≈ 帧率**(即 1 秒一个 GOP): 间隔越大, "开始播放/切换"等得越久。
  ⚠️ 这正好解释我们 A20 里"切段/看最新"要等**下一个 IDR**这件事 —— 我们的 GOP=30(1 秒 @30fps),
  所以最坏等 1 秒; 这是可调的旋钮。

### 3.2 交互层(决定"好不好用")

真实产品里反复出现的模式:
- **主从布局**: 大画面 + 侧边设备/录像列表(海康 iVMS、Shinobi、Blue Iris 都是);
- **时间轴 = 主交互面**: 拖时间轴 = 选时间; 颜色区分钟/事件/锁定; 双击放大到小时/天;
- **多画面墙(n×n 宫格)**: 多摄像头时的默认视图(我们只有一路, 但可以做成"时间墙": 同一路的不同时段);
- **状态永远可见**: ● 录像中 / 存储剩余 / 码率 / 丢帧(工程师视角的"心率");
- **"跳回实时"** 一键(Frigate/海康都有);
- **移动端优先**: 竖屏 = 单画面 + 底部时间轴; 横屏 = 全屏 + 悬浮控制。
- **PWA/离线**(Frigate 有 PWA 文档): 装到桌面/手机; 我们的页面同样可以加
  `manifest.webmanifest` + 一个图标(但**不能引外网**)。

### 3.3 数据可视化层(用户要的"数据图")

对照 Frigate 的 System 页 + 社区 Grafana 面板, 监控系统里最常见的六类图:
1. **码率 / 帧率**(随时间, 折线或 sparkline);
2. **丢帧归因**(堆叠柱: 队列满 / 磁盘满 / 网络错 / 编码错);
3. **存储**: 已用/上限、写入速率、**还要多久写满**、环形覆盖"下一段将被删的是哪一段";
4. **队列水位**(发送队列 / 录制队列的占用与峰值);
5. **摄像头/服务健康**(每个客户端: 传输方式、是否在等 IDR、帧龄);
6. **事件/录像密度热力图**(一天 24 小时的录像/事件分布; 录像检索时最好用)。

## 4. 多客户端能力:我们现在到底支持几个(逐条给依据)

| 通道 | 上限 | 依据 | 备注 |
|---|---|---|---|
| **RTSP/RTP 实时**(VLC/ffmpeg) | **8 个** | `svc_net.h: SVC_NET_MAX_CLIENTS 8`、`svc_sender.h: SVC_SENDER_MAX_CLIENTS 8`;A13 已实测 **2×UDP + 1×TCP 交错同时拉** | 单发送线程轮询多客户端; 每客户端独立会话(RTP 序号/时间戳) |
| **MJPEG 实时**(浏览器 `<img>`) | **4 个** | `svc_live.h: SVC_LIVE_MAX_CLIENTS 4`;满了回 **503** | ⭐ **一帧只编一次, 广播给所有观看者** —— 4 个人看和 1 个人看, 编码开销一样(这是我们比"每客户端转码"的方案省得多的地方) |
| **回放 HTTP**(列表/取流/锁定) | **1 个**(串行) | ADR-5;`svc_http.c` 单线程一次服务一个请求 | ⚠️ **真正的短板**: 有人在下载 900MB 分段时, 别人连列表都刷不出来。但"只连不读"不会卡死(B041, 超时主动丢连接) |
| **录像** | 与客户端数无关 | 录制是独立线程 + 独立队列 | 观看者再多也不影响写盘(两条独立队列) |
| **页面本身** | 无限制(每请求 1 条短连接) | 同上, 串行但快 | 页面每 5 秒拉一次 `/status` + `/recordings` |

**结论**:日常"多人看"完全够(RTSP 8 / MJPEG 4);**唯一会在真实使用中暴露的是"多人同时拖回放"**。
另外两点如实说明:
- ⚠️ **4 个 MJPEG 客户端时板子的表现我没实测**(目前只测过 1 个客户端: 17.2fps、主路 31.5fps)。
  按设计"一帧编一次广播"应该没问题, 但**要压一遍才算数**(建议 2/4 客户端 + 同时录像, 看主路 fps 与丢帧)。
- 浏览器侧: 每个 `<img>` 占一条长连接; 常见浏览器对**同一 源**有约 6 条并发连接的上限
  (端口不同算不同源 ⇒ 我们 8081 的流不吃 8080 页面的配额)。这条是**通用行为, 未实测**。

## 5. 我们已有的"数据" vs 想画图还缺什么

**已经有(在 `*_stats_t` 里, 只是没对外暴露)**:

| 来源 | 字段(举例) | 能画什么 |
|---|---|---|
| `svc_media` | `frames` `bytes` `get_errors` `parse_rejects` `queue_dropped` `record_dropped` `oversize` | 取流 fps、入队码率、**丢帧归因** |
| `svc_sender` | `frames_sent` `packets_sent` `bytes_sent` `send_errors` `waiting_idr` `clients_joined/left` + **帧龄** min/max/last(±漂移) | 每客户端发送量、RTP 包率、**帧龄(延迟代理指标)** |
| `svc_net` | `conns_accepted/rejected/closed/timeout` `requests` `parse_errors` `oversize_drops` | 谁在连、被拒/超时趋势 |
| `svc_record` | `segments` `frames_written` `bytes_written` `deleted` `oversize` `write_errors` `disk_full` `write_retry_ok` `raw_bytes` | 写入速率、**环形覆盖次数**、盘满事件、侧车开销 |
| `svc_http` | `requests` `files` `partials`(206) `locks` `not_found` `bad_requests` `bytes_sent` `rotates` | 回放使用情况、Range 使用率 |
| `svc_live` | `conns` `frames` `bytes` `dropped` `frame_errors` `clients` | 实时观看人数、MJPEG 帧率/码率、**被丢的慢客户端** |
| `svc_record_list()` | 每段: 名字/大小/是否锁定 | 段大小分布、锁定占比、时间轴密度 |

**缺(要加才能画"真实监控那种图")**:

| 缺口 | 加什么(小) | 用途 |
|---|---|---|
| **没有历史** —— 全是累计计数器, 页面只能算"瞬时速率" | 板子上一个 **1 Hz × 60 的采样环**(60 × ~48B ≈ 3KB 静态) + `GET /stats` 吐 JSON | 折线/sparkline、最近一分钟趋势 |
| **没有存储占用** | `statvfs()`(取流/录制已经在用) + 环形上限 → "已用/上限/还能录多久" | 存储环形图、**"下一段会被删的是哪段"** |
| **没有系统资源** | `/proc/loadavg`、`/proc/meminfo`(MMZ 用 `HI_MPI_SYS_GetMemInfo`?) | CPU/内存小图(注意: **温度没有现成接口**) |
| **没有逐客户端明细** | 把 `svc_sender` 的每客户端字段(IP/端口/传输/等 IDR/已发帧)暴露出来 | 客户端表 |
| **没有事件** | 见 §6-B 的运动检测 | 时间轴事件标记 + 事件列表(最有产品感的一块) |

## 6. 设计选项(A/B/C)与"创新点"

### A. 数据面板版(**轻**, 建议先做)

- 板子:加 `GET /stats`(采样环 + statvfs + 现有 counters 的**增量**)。
- 页面:纯前端手写 sparkline(Canvas/SVG, **不引图表库** —— 板子没外网), 四张小卡:
  **码率 / 帧率 / 丢帧归因 / 实时观看人数**;
  一块 **存储环形图**(已用 vs 上限; 锁定段单独标注; "还能录 ~N 小时");
  一块 **段大小分布**(直方图, 直接来自 `/recordings`);
  一张 **客户端表**(RTSP 谁在看/传输方式/是否等 IDR、MJPEG 几个人、HTTP 是否有人在下载);
  一条 **"正在录"进度条**(当前段已录多久 / 段长上限) —— 顺带把"看最新的缺口"可视化了。
- 工作量: 后端 ~150 行 + 前端 ~300 行; **不新增线程/不碰 MPP**, 风险低。
- 面试价值: 高("我知道监控系统该盯哪些指标")。

### B. 事件版(**中**, 最能出彩)

- **加"运动检测"(不用 AI)**: 在**已有的 VPSS chn2(640x360)** 上按 16×16 分块做帧差,
  得到每秒一个"运动分数"; 阈值以上 = 一个**事件**(带起止时间)。
  这条只要碰 VPSS 取帧 + 一个纯函数打分(可 PC 单测), 不引第三方库。
- 有了事件就能做真监控产品的那套:
  **事件列表**(点击跳到那个时刻)+ **时间轴事件标记/热力条** + **"只看有事件的时段"**;
- 顺带实现 **Frigate 式的"智能降级"**: 无运动时把 MJPEG 降到 1fps(甚至停), 有运动时回到 15fps ——
  **省带宽 + 省卡**, 而且我们"按需启停通道"的机制已经在了, 加档位很自然。
- 工作量: 后端 ~250 行(含单测) + 前端 ~150 行; **要重跑 A22 那套验收**(动了 VPSS/通道)。
- 风险: 多一路 VPSS 取帧 + 帧差会吃 CPU(A7 双核), 需要实测; 检测质量只做"有/无运动"级别。

### C. 专业化版(**重**, 看你要不要"标准可接入")

- **回放服务改成可并发**(ADR-5 的升级路径: 每客户端一线程 或 epoll 状态机 + 发送游标);
- **fMP4/MSE 实时**(低延迟、可上原生分辨率): 要自己写分片封装(mp4v2 不支持 fMP4),
  或**内置 go2rtc 那种"按需转码"的极简版**;
- **ONVIF Profile G/S 接口**(让 Frigate/Blue Iris/群晖直接接入我们, 而不是我们做客户端)——
  这是"设备侧标准化"的路线, 面试讲"设备接入生态"很有料, 但工作量大;
- 鉴权(现在**完全没有**)、TLS、PWA 安装、多语言。

### 创新点(相对"抄一个 NVR 界面", 这些是我们能做而大厂不一定做的)

1. **"缺口的可视化"**:把"正在录的这一段还不能回放"画成一条**会随时间缩短的缺口**,
   配合 `/recent.mp4` 的"收尾后立刻可看" —— 这是**我们的实测特性**, 现成产品通常直接隐藏。
2. **锁定段 + 环形覆盖的"沙盘"**:把那句"字典序=时间序, 满了删最旧"**画出来**
   (下一段将被删的是谁、锁定段像钉子一样钉住) —— 面试时这是最能讲清设计的一句图。
3. **断电恢复的"考古视图"**:把 `*.h264.tmp` 侧车 → 重封成 `.mp4` 的**恢复记录**列出来
   (哪一段是掉电救回来的、救回多少帧) —— 独此一家, 因为别的方案没这个机制。
4. **"一帧编一次, 多人共享"的实时视图**:页面上显示"3 人在看, 编码开销不变",
   把架构优势**变成可见的事实**。
5. **时间墙**(单路摄像头的替代玩法):同一路的不同时段并排(比如"整点各一张"),
   比多画面墙更适合单摄像头场景。

## 7. 我们**不建议**做的

- ❌ 引 Tailwind/React/Chart.js 这类 CDN 或构建链: 板子常常没外网, 引了就是白屏风险;
  而且现在"一个常量字符串、零构建"本身是**优点**(面试可讲)。
- ❌ 为了"好看"把 MJPEG 换成 WebRTC: 那是**重写传输栈**(信令 + DTLS/SRTP),
  收益只有延迟, 风险远大于收益。想要低延迟就先把 **MJPEG 的 GOP/帧率/质量**调好。
- ❌ 做多摄像头宫格: 我们只有一路。
- ❌ 一上来就做鉴权/TLS: 定位是局域网演示, 明确写在文档里即可(现状已如实声明)。

## 9. Gaps 与未定论(不许含糊的地方)

- **多客户端实测缺失**: 4 个 MJPEG 同时看 + 录像时的主路 fps/丢帧**没量过**;
  浏览器的**同源 6 连接上限**也没在真机上确认(不同端口算不同源, 理论不影响 8081)。
- **延迟只有估计**: MJPEG 那一路没有 OSD 水印, 端到端延迟目前是"分量相加 150~250ms"的**估计**,
  不是实测。要给真数, 得先给 MJPEG 通道也挂一个 REGION(见 STATUS 的 A22 后续)。
- **温度/硬件健康**没有接口(`/sys/class/thermal` 在这颗板子的内核上没确认过)。
- **运动检测的 CPU 代价**没量过; Hi3516DV300 是双核 A7, 帧差要用**子采样 + 16×16 分块**才划算。
- Frigate 的 `mse/webrtc` 细节来自其官方文档(§2 来源 1), **我们没有复现它的实现**,
  只作为设计参考。
