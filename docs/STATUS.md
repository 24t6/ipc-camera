## 二、关键设计决策(附理由)

| 决策 | 理由 | 备选与为什么不选 |
|---|---|---|
| **分段边界对齐到 IDR(关键帧)** | "数够 N 帧就切"会在刀口上丢帧 —— 新段建轨需要 SPS/PPS(跟着 IDR 一起来),等它到达期间那些帧就被丢掉了(实测每段丢 29 帧 ≈ 1 秒)。改成:**收满后继续写当前段,遇到下一个 IDR 才关旧段,并用这一帧开新段** | ffmpeg `segment` muxer 的官方行为也是"从指定时间**之后第一个关键帧**开始",与此一致 |
| 默认**每段 30 分钟**;环形上限 `-r` **必须大于一段** | 30 分钟是监控行业惯例(NVR/DVR 普遍 30 或 60 分钟)。⚠️ 上限若小于一段,环形覆盖会**静默退化成"只留一段"** | 段太短 → 文件数爆炸;段太长 → 掉电一次丢太多 |
| ⭐ **分段依据 = 时间到 或 大小到(谁先到算谁)**, 默认 30 分钟 / 1024 MB | 只按时间切时, 段大小 = 时长 × 码率, 而码率随画面复杂度浮动 ⇒ 有可能冲破 vfat(FAT32)的 **4 GiB 单文件硬上限**, 那会在**段中间**写失败。加一条大小上限, 文件大小就有确定性上界。判据用的是**真正落盘的码流字节数**(不是"处理过多少") | ffmpeg `segment` muxer 只有按时间/分片数;海康 SDK 是**按字节切**。我们**两个都要**, 因为两者的失效模式不同(时间→掉电丢得多;大小→撞 FAT32 上限)。**大小上限故意不提供"关闭"**(配置里 0 = 用默认), 要放宽只能设接近 4 GiB 的值, 启动时告警 |
| **环形覆盖**按文件名排序删最旧 | 文件名零填充 `YYYY-MM-DD-HH-MM-SS.mp4` ⇒ **字典序 == 时间序** | 厂商 sample 用 `%d-%d-…`,`2026-9-16` 会排在 `2026-10-1` **后面** ⇒ 删错文件 |
| **锁定段保护**:清单文件 `<dir>/.locked`(每行一个文件名), 被锁的段**跳过不删** | 行业通用语义(海康"锁定后不会被覆盖"; ISAPI `lockStatus`)。用**纯文本清单**而不是文件属性(vfat 的 `FAT_IOCTL_SET_ATTRIBUTES` 不可移植)也不是改名(会同时破坏"字典序==时间序"和 `*.mp4` 扫描约定)。清单是**唯一真相源** ⇒ 策略层仍是纯函数(只吃一个布尔量), 阶段 2 的管理接口只需读写这个文件 | 数据库/单独目录: 都要么引依赖、要么破坏"一个目录就是全部录像"的简单模型。⚠️ 锁定段**照样占容量**: 全锁定时清理删不动, 此时明确报错而**不自动解锁**(锁是用户的意图) |
| 覆盖决策是**纯函数** + 单元测试 | "该删哪几个"与"真的 `unlink`"分离 ⇒ 决策可在 PC 上原生单测(现有 **23 条断言**) | — |
| **优雅关闭**(捕获 `SIGINT`/`SIGTERM`) | MP4 的索引 `moov` 只在 `MP4Close` 落盘;不优雅关闭 ⇒ 整个文件打不开 | 真断电无法避免 —— 只能靠**分段**把损失限在一段内 |
| **单路编码**(不做主/子双码流) | 在这颗芯片的 MPP 上,**启动一个没人取流的编码通道会把整条流水线拖死**(实测固定卡在 205 帧) —— 未消费通道的缓冲塞满 → 编码器停 → 反压到 VPSS | 真实 IPC 通常同时编 2~3 路;多路的前提是每路都有消费者 |
| VENC 通道与 VPSS 通道**成对选择**,全文件不写死通道号 | 同类错误在"切到另一路"时会整体失效 | — |
| TF 卡用 **vfat** 而不是 ext4 | SD 协会规定 SDHC(≤32 GB)用 FAT32(**合规**),且 vfat 能**拔卡插电脑直接看** | Axis 官方建议监控卡用 ext4(断电后恢复更快、更不易损坏)—— 这是**知情的取舍**,代价是寿命与空间利用率 |
| **不采用 fMP4** | ① 没找到任何厂商公开文档说机内录像写 fMP4(采用证据都在流媒体侧 DASH/HLS/CMAF);② 所用库 **mp4v2 结构上不支持** —— 14 个头文件里 `moof`/`mvex`/`tfhd` **零命中**,源码里只有一行未实现 TODO;③ 实测它的收益与"旁路裸流"相同 | 详见 §3.9 与 [`docs/research/`](research/) |
| 发送与录制用**两条独立队列**(在取流处扇出) | 磁盘慢只丢录制的帧、网络慢只丢发送的帧 | 否则"存储坏了 = 直播也看不了";单队列两个消费者会各拿一半帧 |
| **正在写的段用 `.tmp`、收尾才 `rename`** | 让"这段是否完整"成为目录里**一眼可见**的状态:目录扫描只认 `.mp4`,半成品既不进环形容量、也不出现在检索列表。依据是 Axis 边存官方的 `recording.tmp` 模式("写完才对外可见") | 只在收尾时改名;极少数情况下 `rename` 失败会留下 `.tmp`,由启动清理兜底 |
| **旁路裸流侧车** `<stamp>.h264.tmp`(默认开,`-no-raw` 可关) | 断电/强杀时 MP4 **一定**打不开(没写 `moov`),而**同内容的 Annex-B 裸流被截断也能解** —— 实测同一时刻:残段 0 帧、**侧车 315 帧**。侧车只在"这一段进行中"存在,收尾即删 ⇒ **稳态磁盘占用不变**,环形覆盖一行没改 | 写入量翻倍(卡寿命约 6 年 → 约 3 年);不调 `fsync`,断电最多丢约 30 秒侧车(升级路径写在代码的【简化上限】里) |
| **回放列表默认只给"最新一页"(64 条)+ `?limit=&before=` 翻页** | 运行期不做动态分配 ⇒ 列表得用**文件级静态数组**, 容量写死。全量返回在段数多时既撑不住也"用户根本看不出重点"; 而回放**最常看的就是最新那段** ⇒ 默认视图给最新的 64 条, 更早的用 `before=<当前页最后一条>` 翻。判据是"第一条 == 卡上最新的 `.mp4`"(`STATUS` A19) | 一次性全量返回: 段数无上限, 静态数组一定被撑爆。⚠️ 代价: **"先填满数组再排序"是个真 bug**(B044)—— 那样留下的是 `readdir` 先遇到的 64 个, 恰好都是旧的, 表现为"刷新多少次都只看到几小时前"。正解是**边扫边淘汰**(留下最新的 K 个) |
| ⭐ **"看最新"= 让录制线程切一段, 而不是自己重封一段** | 正在写的 `.tmp` 没有 `moov` ⇒ 播不了。让**已有的切段路径**提前跑一次(下一个 IDR 处关旧段、用这一帧开新段), 那一秒后就有一个完全正常的 `.mp4`:边界仍对齐关键帧、**一帧不丢**、`Range` 直接可用、**不用碰 mp4v2 的跨线程问题**、也不用估算"N 秒大概多少字节"。判据见 A20 | 被否掉的方案:**把旁路裸流侧车尾部 N 秒重封** —— ① 得按码率**估算**字节位置(估不准);② 要在另一个线程动 mp4v2(库的全局状态 + 录制线程正在用);③ 重封期间录制队列被挤满会丢帧(与 A12 同代价)。⚠️ 代价:每次请求**多一个分段边界** ⇒ 加 20 秒"段太新就不切"的保护 |
| ⭐ **"正在录的那一段看不到"是设计行为, 不是 bug** —— 用 `/status` + 页面"正在录"横幅把它**显式化**, 用**段长**控制缺口大小 | 正在写的段是 `<stamp>.mp4.tmp`(见上一条), 它不进列表/不占环形容量, 代价就是"离现在最近的这段(默认 30 分钟, 现在板上设 300 秒)在段收尾前任何客户端都取不到"。行业同样如此(Axis 的 `recording.tmp`), 因为 **MP4 的索引 `moov` 只有关文件时才写**: 没 `moov` 的文件给了播放器也打不开, 让它出现在列表里反而是**假承诺**。所以不做"假装能看", 而是: ① 新增 `/status` 如实报告".tmp 有多长、录了多少帧、从几点开始"; ② 页面顶部横幅显示"● 正在录 …"和"最新可看 = 上一段"; ③ 想缩小缺口就**把段长调短**(`-s 300` = 最多落后 5 分钟), 这是唯一正确且无副作用的旋钮 | ① 把 `.tmp` 当 `.mp4` 列出来: 用户点了必然打不开(没有 `moov`)。② 边写边发 fMP4(`moof`): 需要分片索引, 而 **mp4v2 结构上不支持**, 且会推翻"断电残留靠侧车裸流救"的整套设计(见 §2 与 B034 的调研)。③ 内存里攒一段再落盘: 一段几十 MB, 板上没有这个余量 |
| **开机自动把残留侧车重封成 MP4**(`recover_leftovers()`) | 侧车若只能"拷到 PC 上转",就等于**没有**掉电保护 —— 板子自己转, 用户拿到手就是能播的文件。复用与正常录制**同一套** mp4v2 调用(不是第二套封装代码),所以结果与录像完全一致 | 这一步**同步跑在录制线程里**,期间实时帧会被队列丢掉(实测 81 MB → 13 秒 → 丢 173 帧);升级路径 = 改成独立低优先级线程,已用 `【简化上限】` 标注 |

## 三、已知问题与技术债(诚实清单)

> 这一节是**故意公开**的:一个能说清"哪里还没做好"的项目,比一个声称全都做好的项目可信。

| # | 问题 | 影响 | 计划 |
|---|---|---|---|
| 1 | ~~**RTSP over TCP(RTP 交错)一帧都发不出去**~~ | ✅ **已解决(2026-09-18)**。查出来是**两个**根因:① `svc_sender` 不看传输方式, 一律建 UDP sender(TCP 时往"RTP 端口 0"发);② **更本质** —— 发送主路径 `emit()` 直接调 `proto_rtp_send_nalu()`(里面自己 `sendto`), **绕过了传输抽象**, 所以 TCP sender 建了也不被调用。修法:新增 `infra_transport_t` 由 `svc_net` 交出传输方式 + 把 `proto_rtp` 的"打包/发送"拆开(新增 `proto_rtp_pack_nalu(cb)`, `send_nalu` 保留为薄包装) | 已完成 |

## 四、行业调研(不是"我觉得", 是有来源的)

就"掉电怎么办、卡满怎么办、客户端怎么做回放"做了 5 路带来源的调研:

- **共 133 条来源,其中官方文档/标准 92 条(69%)**;每份笔记都带
  **来源类型 / 页面日期 / 证据强度分层**(规范原文 → 社区实现源码 → 二手转录)与 **Gaps**。
- 笔记在 [`docs/research/`](research/):掉电保护 / 存储生命周期 / 厂商与标准 / 开源实现 / 客户端与回放。
- **结论汇总表**(行业做法 → 本项目的决定 → 明确不做什么)在
  [`PROJECT_PLAN.md` §3.9](PROJECT_PLAN.md)。

几条值得单独说的调研结论:

1. **ONVIF Profile G 完全不管分段** —— 规范全文里 `Segment`/`Retention`/`Storage`/`Export`
   命中**全为 0**。所以**不能**用"符合 Profile G"来论证分段策略。
2. **行业没有统一的"预留 xx%"水位** —— 流传的"不超过 80%"都出自容量规划建议,
   不是运行时参数。有具体数值的是开源实现:ZoneMinder 出厂 `DiskPercent>=95` + 删最旧;
   Frigate 用"剩余不足约 1 小时录像量"。
3. **"段中间盘满"没有任何开源项目专门处理**(它们都是周期性轮询)——本项目的处理会超出常见实践。
4. **海思官方 sample 零分段逻辑**:只有 `SAMPLE_COMM_VENC_SaveStream` 存**裸码流**,
   全文件**没有任何 MP4 调用** ⇒ **"MP4 封装 + 分段 + 环形覆盖"完全是自己实现的**。

## 五、编译与复现

```bash
# 交叉编译(需要海思 SDK 与 arm-himix200 交叉工具链, 参见 README)
# 产物 ipc_app 部署到板子后:
./ipc_app -p 8554 -s 1800 -r 8192     # 默认: 每段 30 分钟 / 环形上限 8 GB

# 拉流(把 <board-ip> 换成板子地址)
ffprobe -rtsp_transport udp -i rtsp://<board-ip>:8554/live
ffplay  -rtsp_transport udp rtsp://<board-ip>:8554/live
```

| 选项 | 说明 |
|---|---|
| `-p <端口>` | RTSP 端口(默认 8554) |
| `-s <秒>` | 每段多少秒切新文件(默认 **1800 = 30 分钟**) |
| `-r <MB>` | 环形容量上限(默认 **8192**;⚠️ **必须大于一段**) |
| `-no-record` | 不录 MP4 |
| `-no-osd` | 不叠时间水印 |
| `-h265` | 取 H.265 那一路(默认 H.264 720p)。⚠️ mp4v2 不支持 H.265 封装,该模式下**录制会自动关闭** |
| `-H <端口>` | **回放服务(HTTP)端口**(默认 **8080**;`-no-http` 可整个关掉) |
| `-no-http` | 不起 HTTP 回放服务(只留 RTSP 推流) |
| `-L <端口>` | **实时画面(MJPEG)端口**(默认 **8081**;`-no-live` 可关掉) |
| `-no-live` | 不起实时画面服务(回放/推流/录制照常) |
| `-v` | 打开 DEBUG 日志 |

回放服务(阶段 2,`http://<board-ip>:8080/`):

| 路径 | 说明 |
|---|---|
| `/` | 板子自己发的**回放页面**(分段列表 + `<video>` + 时间轴 + 锁定/另存 + "● 正在录"横幅, **每 5 秒自刷新**) |
| `/status` | **正在录**的那一段:名字 / 已写字节 / 帧数 / 起始时间 / 直播地址(JSON) |
| `/recent.mp4` | **"刚录的这段"立刻能看**:请录制线程把当前段收尾, 再发刚收尾的那一整段(支持 `Range`);应答头 `X-Recent-Clip` 告诉你拿到的是哪一段;没在录 ⇒ 503 |
| `/status` 里的 `live_mjpg` | **实时画面(MJPEG)的 URL**(形如 `http://<板子>:8081/live.mjpg`)—— 页面用它显示 `<img>` |

实时画面走**另一个端口**(默认 8081, `-L` 改、`-no-live` 关):

| 路径 | 说明 |
|---|---|
| `/live.mjpg` | **MJPEG 流**(`multipart/x-mixed-replace`):浏览器 `<img src=...>` 直接显示, **零安装**;`/live`、`/stream` 等价 |
| `/help` 等其它路径 | 404(它不是回放服务, 只有这一条流) |
| `/playlist.m3u` | 给 VLC/mpv 的**整段**播放列表(旧→新, 绝对 URL) |
| `/recordings` | 分段 JSON 列表, **默认最新 64 条**, `?limit=&before=` 翻页 |
| `/recordings/<名字>` | 取某一段(GET/HEAD, 支持 `Range` → 206) |
| `/recordings/<名字>/lock` | `PUT` body `1` 锁 / `0` 解锁(被锁的段环形覆盖不删) |
| `/help` | 纯文本接口说明 |
